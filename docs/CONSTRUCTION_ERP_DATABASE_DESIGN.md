Migration rules:
- Runner: `src/core/utils/migrator.js`. Applies pending files in name order, one transaction per file, records names in `sequelize_meta`.
- Rollback removes the last applied migration by name. The project master rollback is refused on SQLite when `PROJECT` rows exist.
- `scripts/sync-models.js` and `scripts/sync-procurement.js` no longer use alter-mode synchronization. They refuse to run unless the explicit development guard passes (`scripts/schema/dev-sync-guard.js`).

## 3. Ownership of the 75 tables

- 47 tables are created by the generated baseline.
- 28 tables are created by migrations: 21 by migrations 3 to 12, and the 7 project master tables by migration 15. Migrations 1, 2, 13 and 14 add columns, indexes or constraints only.
- The baseline generator excludes from the baseline every table that a migration creates and every column or index a migration adds. The exclusion is deliberate: it avoids creating a table or column twice. The generator scans migration files for `createTable`, `addColumn` and `addIndex` calls, accepting both single and double quotes (fixed in this phase).
- `PROJECT` columns added by migration 15: `project_code`, `contract_type`, `currency`, `start_date`, `location_name`, `description`, `client_id`, `consultant_id`, `project_manager_id`; plus unique index `ux_project_company_code`.

## 5. Keys, integrity and money

- Primary keys: integer auto-increment `id` on every table.
- Tenant column: `company_id` on company-owned tables. Project-owned tables also carry `project_id`.
- Foreign keys use `ON DELETE CASCADE` for ownership (company, project) and `SET NULL` for optional links. `NO ACTION` is used for a few references (for example `CONTRACTOR_RA_BILLS.vendor_id`).
- Uniqueness within scope: project codes per company (`ux_project_company_code`); structure codes per project (`ux_project_phase_code`, `ux_project_zone_code`, `ux_project_discipline_code`, `ux_project_cost_centre_code`, `ux_project_work_package_code`); client and consultant names and codes per company.
- Money and quantities use `DECIMAL` with the precision set in each model. Rounding and precision policy is not documented in a single place; this is an open item.
- Timestamps: `createdAt`, `updatedAt` on most tables. Some ledger tables use `createdAt` only.
- JSON columns: used for `PROJECT_HISTORY.meta`, the `detail` text of stock transfer events, and a small number of other fields. Not used for filterable relationships.

## 6. Known database gaps (verified)

These are described in the audit document and the implementation log. Summary:

1. No entities exist for branches, departments, purchase requisitions, RFQ line items as separate records, inspection plans, NCRs, HSE incidents, RFIs, submittals, transmittals, handover records, DLP defects, general ledger accounts, journal entries, receivables or payroll.
2. The stock ledger has no reservation table. Reservations, picking and damaged-stock status are not modelled.
3. Project reallocation between projects is blocked by a server-side gate (HTTP 409). Its ledger replacement is not implemented.
4. MySQL/MariaDB has not been verified for any migration, including the baseline. Sequelize ENUM and JSON types behave differently on MySQL; this must be checked before production use.
5. Demo database `demo3.sqlite` (C:, scratchpad) has the tables but no `sequelize_meta` record. It is `ADOPTION_REQUIRED`. It has not been migrated or stamped.
6. D-1 is resolved: the unique index `PROJECT_TASK_ASSIGNEE_user_id_task_id_unique` duplicated the composite primary key and is dropped by migration 16. D-2 (declared types), D-3 (defaults) and D-4 (ON DELETE actions) are open between the models and the migrations; see section 7.
